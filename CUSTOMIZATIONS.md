# Customizations

Record of the changes made to this repository and why. Newest last.

---

## 1. `9e1c9e5` — feat(pwa): installable app that works fully offline

Request: *"Turn this web app into pwa so it can be installed and used offline."*
Offline had to cover **all** features: camera scan, image-file scan, QR generation,
and history.

### What changed

| Area | Change |
|---|---|
| Build | Added `vite-plugin-pwa` (devDep) driving Workbox `generateSW`; `registerType: "autoUpdate"`. |
| Manifest | Now generated by the plugin from the `manifest` option; the link is injected into `index.html` at build time. |
| Dead config | Deleted the tracked root `manifest.json`. |
| Icons | Added `public/icons/icon.svg` + `icon-maskable.svg` and committed 192/512 PNGs. |
| Offline decoder | Added `public/zxing/zxing_reader.wasm` and an Emscripten `locateFile` override in `src/utils/scanImage.ts`. |
| Registration | `navigator.serviceWorker.register()` in `src/main.tsx`. |
| Docs | New "PWA / offline" section in `architecture.md` and README. |

### Why

**The manifest was never actually shipped.** The root `manifest.json` was dead
source: `public/` contained no manifest, so Vite never copied it, and the `docs/`
build referenced a manifest that did not exist there. The plugin now generates
it, so it cannot drift from the config.

**Offline image scanning would have failed silently — the load-bearing fix.**
`barcode-detector` → `zxing-wasm` downloads its WebAssembly binary from
`fastly.jsdelivr.net` at runtime through Emscripten's `locateFile` hook. Caching
the app shell would therefore have cached *everything except the one binary image
decoding needs*: the app would install, open offline, and fail only when scanning
a file. The binary is now committed from
`node_modules/zxing-wasm/dist/reader/` (SHA-256 verified against the library's
own `ZXING_WASM_SHA256`) and `setZXingModuleOverrides({ locateFile })` redirects
the load to it. Only the *reader* variant is vendored — encoding uses the pure-JS
`qrcode` library — and any other variant falls back to the CDN. The path derives
from `import.meta.env.BASE_URL`, and `resolveWasmPath` is pure and unit-tested.

**The plugin's own registration helper broke offline.** `virtual:pwa-register`
dynamically imports a `workbox-window` chunk that Vite emits *after* Workbox has
built its precache manifest, so the chunk was never precached and its `import()`
rejected with `ERR_INTERNET_DISCONNECTED` on every offline start (observed in the
network log). Registration is now a plain `register()` call. Nothing is lost:
`registerType: "autoUpdate"` already emits `skipWaiting()` + `clientsClaim()`, so
a new build activates on the next reload — confirmed present in the generated
`docs/sw.js`. Dropping the update manager means updates apply on next navigation
rather than mid-session; accepted, since this is a stateless utility.

**Icons are committed, not generated in CI.** The runner is `ubuntu-latest`, which
has no SVG rasterizer, so generating them at build time would have been a
silent-failure source. They are rasterized once with macOS `sips` and committed;
the command is documented in the README.

**Precache scope** is deliberately 10 entries: the shell, hashed JS/CSS, the
manifest, the icons, and the wasm. `sw.js` and the Workbox runtime are excluded,
or the browser could never see a new service worker.
`maximumFileSizeToCacheInBytes` is raised because the wasm is ~919 KiB. Icons come
from `includeAssets` and the wasm from the `wasm` glob — listing either in both
places produced duplicate precache entries. `devOptions` is off so the dev server
cannot serve a stale shell.

## 2. `235da1d` — fix(pwa): derive every base-dependent value from one source

Found by an independent code review of `9e1c9e5`, not by the tests.

### What changed

| Area | Change |
|---|---|
| `vite.config.ts` | Config is now a function of Vite's `mode`; `BASE = mode === "root" ? "/" : "/qr-scanner/"` feeds the Vite base, the manifest's `id`/`start_url`/`scope`, and the SW `navigateFallbackDenylist` (built with `new RegExp`, escaped). |
| `index.html` | Icon hrefs use `%BASE_URL%` instead of a hardcoded `/qr-scanner/…`. |
| `package.json` | `build:local` is `vite build --mode root` (was `--base /`); added `check:wasm`. |
| `scripts/check-wasm.mjs` | New guard: hashes the vendored wasm against the installed version's exported `ZXING_WASM_SHA256`. |
| CI | New "Verify vendored wasm" step before the build. |
| Docs | README + `architecture.md` record the one-source rule and the guard. |

### Why

**The bug.** `build:local` ran `vite build --base /`, but `--base` overrides
Vite's own `base` while leaving values baked into the manifest, the Workbox
config, and `index.html` untouched. A root-base build therefore emitted
`start_url`/`scope`/`id` = `/qr-scanner/`, a denylist of
`/^\/qr-scanner\/assets\//`, and icon hrefs pointing at `/qr-scanner/…` — an
installed PWA scoped to a path it was not served from. Measured before the fix,
not theorised.

**Why it survived review by tests.** Nothing tested a non-default base, so every
suite stayed green while the local build was broken. The failure was in the
*interaction* of two individually-reasonable choices (a CLI flag and inlined
paths), which is why the fix is structural: there is now exactly one source of
truth, and it cannot disagree with itself.

**Mode naming.** The mode is `root`, not `local` — Vite rejects `local` as a mode
name because it collides with its own `.env.local` postfix convention. This was
hit during verification and is recorded to save the next attempt.

**The guard exists because the drift failure is silent.** Nothing tied the
committed wasm to the installed package, so a `zxing-wasm` bump that refreshed
`node_modules` without re-running the documented `cp` would leave a stale binary
and break image scanning **offline only**, with no build error. `check:wasm`
compares the file against the library's own assertion and fails loudly; CI runs
it before the build.

## Verification practice used for these changes

- `tsc --noEmit`, `vitest run` (74 tests), and `vite build` on every change.
- Both bases built and probed for `id`/`start_url`/`scope`, icon hrefs, denylist,
  and precache count — the check that would have caught the base bug.
- `check:wasm` mutation-tested rather than assumed: pristine `0`, corrupted `1`,
  restored `0` byte-identical.
- Offline relaunch reproduced in a real browser with a cross-origin canary
  proving the network was genuinely down, and the wasm confirmed served from
  cache (`\0asm` magic, 940,931 bytes).
- `bun install --frozen-lockfile` run locally to pre-validate CI's install step.

### Known residual issues

- `scripts/check-wasm.mjs` imports `zxing-wasm/reader`, which is a *transitive*
  dependency of `barcode-detector` and is not declared in `package.json`. It
  resolves under a flat `node_modules` and fails loudly if it ever stops
  resolving. Declaring `zxing-wasm` explicitly as a devDependency would be more
  correct; left unchanged to avoid a lockfile churn.
- `public/style.css` defines a `--animate-scan` theme token, but `animate-scan`
  is referenced nowhere in `src/`. Pre-existing and untouched.
